## 1. 目的

入口拒否制御は、侵入要求が session または token になる前に拒否する。遮断条件は、挙動の連鎖と、登録済みの端末・application・権限である。主体名の一致は案件記録に残し、遮断の述語には使わない。

公表された入口は次の三つである。

| 経路 | 一次資料が示す入口 | 拒否する地点 |
|---|---|---|
| Qilin | 2024年7月、盗まれた資格情報で MFA の無い VPN へ入った。初期アクセスから次の操作まで18日 | 対話面。token と VPN session の発行前 |
| ARTEX（Storm-0940） | 2026年9月以降。侵害されたマルチテナント application の資格情報で、利用者の対話ログイン無しに顧客環境へ入った。標的化から特権到達まで3時間未満の事例が複数ある。後続は Microsoft Graph の探索、application 資格情報の変更、特権の変更 | アプリ面。同意済み権限の上限と、ディレクトリ変更の commit 前 |
| 同キャンペーンの password spray | 2026-10-10〜14。8組織、327 account、失敗15.1万件超。10月11日に毎分2,900失敗、1日で11.1万件超。48 account が1,000失敗超。応答の約98%がロックアウト。この spray では成功認証、token 発行、Graph 呼び出し、ディレクトリ変更は観測されていない | 接続連鎖の速度制限。account ロックは行わない |

Huntress（2026-10-26）は、速度と User-Agent はツールの改変で消えるとし、活動の中身を見る方針を示している。本書はペースと User-Agent を単独の遮断条件にしない。

## 3. 構成

強制点は session 確立前に置く。VPN はトンネル確立前、IdP は token 発行前、ディレクトリは変更の commit 前である。発行後の取り消しは第二の手段であり、第一の拒否点にしない。

| 要素 | 責務 | 入力 | 出力 |
|---|---|---|---|
| 観測収集 | 面ごとの事象を同じスキーマにする | VPN、IdP、ディレクトリ監査、おとり | 節4の事象 |
| 連鎖台帳 | 事象を連鎖へ結ぶ | 事象 | 連鎖 |
| 方針評価 | 節6の述語を上から評価する | 連鎖と登録台帳 | 応答クラス |
| 強制点 | 応答を session 確立前に適用する | 応答クラス | 拒否、速度制限、資格情報の無効化、記録 |
| 案件 | 人が調査と復旧を行う | 強制の記録 | 失効、権限のはく奪、application の停止判断 |

対話面とアプリ面で強制点は分かれる。台帳と方針は一つである。

### 3.1 対話面で token を出す条件

次をすべて満たす。

- phishing-resistant MFA がある
- 管理端末の証明書がある
- 対象 account がおとりではない
- 管理操作である場合、専用経路であり、その時間だけ有効な権限である

パスワードが正しいことは、token を出す条件にしない。

### 3.2 アプリ面で操作を許す条件

顧客が終端しないクラウド API では、発行済み token の読み取りを顧客のプロキシで拒否できない。アプリ面の本体は、同意時点の権限の上限である。

- 照合キーは application ID である。表示名では照合しない
- 登録された scope と資源の範囲だけを許す
- service principal 自身による、資格情報の追加、所有者の追加、高権限ロールの付与、同意の拡大は、変更窓の有無にかかわらず拒否する
- 人が行う資格情報のローテーションは、節3.1を満たす変更主体が、登録された変更窓の中で行う
- 接続元 IP は補助属性である。定例操作は、登録 IP と一致しなくても、権限の範囲内なら許す。ディレクトリ変更の拒否は IP に依存しない。Huntress は、application 単独の監査事象に送信元 IP が無い場合があると報告している

初動で enterprise application のオブジェクトは削除しない。監査を保全し、追加された資格情報を無効化し、ロール付与を拒否する。application の停止と権限のはく奪は、案件を受けた権限者が行う。バックアップの停止を自動応答にしない。

## 6. 方針

評価順は P1、P4、P3、P2、P8、P7、A1、A2、P5、P6 である。先に一致した応答を採用する。

| ID | 条件 | 応答 |
|---|---|---|
| P1 | 対話認証が、証明書と phishing-resistant MFA の両方を満たさない | token を出さない。account 状態は変えない |
| P4 | service principal 自身が資格情報を追加する、所有者を追加する、高権限ロールを付与する、同意を拡大する | 資格情報の追加は commit 前に拒否する。所有者、ロール、同意は、その権限を持たせないことで操作自体をできなくし、監査に現れたら取り消す（`precommit-feasibility.md`）。既に入った資格情報は無効化する。application オブジェクトは残す。監査を保全する。案件を開く |
| P3 | おとりへの事象から30分以内 ※要確認に、同じキーで本番の VPN または API へ認証があり、その認証に管理端末証明書が無い | その連鎖を60分 ※要確認 遮断する |
| P2 | 5分以内 ※要確認に、異なる account へ認証失敗が10件以上 ※要確認、かつ端末が不整合 | その連鎖の新規接続を速度制限する。後から節3.1を満たす利用者には追加認証を求める。ロックアウトが失敗の半数を超えたら、account ロックを追加しない |
| P8 | 監査に、登録範囲を超える application 操作が現れる | その service principal の token 更新を止める。案件を開く |
| P7 | 登録済みクローラー、または事前登録した診断窓からのおとり接触 | 記録のみ |
| A1 | 節3.1をすべて満たす対話認証 | 許可 |
| A2 | 登録 application が、登録 scope と資源の範囲で、ディレクトリ変更を含まない | 許可 |
| P5 | 公開 IOC の IP と一致し、上の拒否述語に該当しない | 記録のみ |
| P6 | 公表された User-Agent と一致し、上の拒否述語に該当しない | 記録のみ |

P4 の強制は、監査事象の到着から60秒以内に強制点へ届けることを設計目標とする ※要確認。根拠は、公表事例でツールの変更が約55秒、特権到達が3時間未満であることである。人の当番を、初回応答の経路に置かない。

保全のエクスポートが間に合わない場合でも、P4 の拒否は遅らせない。Microsoft は、証跡の書き出しを待たずに緊急の封じ込めを行うよう述べている。

## 7. おとり

- 隔離した名前空間に置く。本番の資格情報ストア、本番データ、本番の session 鍵へ接続しない
- 置くものは、管理 URL に見える経路と、ログイン名だけである
- 接触だけで主体を断定しない。接触は連鎖台帳へ入れる
- 検索クローラーと診断窓は、事前登録で P7 とする
- `vision.md` の提案である。節12の事例が、おとりへの接触を観測したという意味ではない

## 8. 第二線

目的は入口での拒否である。次は、入口を通過した主体がディレクトリのポリシーを変える場合の拒否である。

既定ドメインポリシーの変更、ログオン時に実行するスクリプトの変更、SYSVOL への書き込みは、専用の管理経路と時間限定の権限が無い主体には拒否する。

Sophos が2024年7月に観測した Qilin の事案では、ドメインコントローラー到達後にログオンポリシーが変更された。本節はその変更を適用させないための認可である。変更手順は本書に書かない。

## 9. 限界

- 節3.1を既に満たす対話 session は、P1 では拒否できない。管理操作は節8で拒否する
- 登録範囲内の読み取りしかしない、盗まれた application 秘密情報は、A2 で許可される。権限の上限を事前に絞ることが、この経路の拒否である。サインイン元 IP の変化だけでは自動遮断しない
- Graph の読み取りログが無い環境では、列挙の有無を証跡にできない。ログが無いことを、アクセスが無いことの証拠にしない。拒否の正本は、token 条件とディレクトリ変更の拒否結果である
- 連鎖キーの衝突率は未計測である
